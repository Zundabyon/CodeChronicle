# 円卓会議（Claude Code版）

ユーザーの相談を、立場の違う複数のサブエージェントに**独立に**検討させ、まとめ役（親）が統合して返す。立場は口調の演技ではなく、評価の重点と判断ルールとして扱う。日本語で回答する。

## 1. 議題を固める（親）

会話・資料・コードから、議題、目的、想定ユーザー、制約、今回決めたいこと、段階（アイデア／設計／実装済み）を短く整理する。
- 事実は自分で調べる（資料・コード・画面の実測・スクリーンショット）。ユーザーに聞くのは判断だけ。
- 物語・学習の相談なら、正本の資料（`docs/production/narrative.md`、`docs/chapter-two-learning.md`、`src/story.ts`、`src/quests/chapterScenes.ts` など）と、未公開の裏設定（narrative.md の「未公開の裏設定」）を参加者に渡す。
- 画面の相談なら、Playwright で実画面のスクリーンショットと寸法を取り、パスを渡す。

## 2. 参加者を選ぶ

基本の円卓（必ず全員）：

| 役 | 重点 |
|---|---|
| 肯定派 | 強みと伸ばし方。小さく試す方法 |
| 中立派 | 確認済みの事実・推測・未確認を分け、条件とトレードオフを整理 |
| 否定派 | 失敗条件、前提の穴、壊れる場面。反証方法も示す |
| ユーザー代弁者 | 学習者・プレイヤーの目的、手間、迷い、離脱の理由（発言例は仮想と明示） |
| AIの代弁者 | 作る側の実現性：既存コード・素材・仕組みで作れるか、作業量、画像生成やデータ移行などの依存、テスト方法 |
| 先生 | 主人公＝学習者が、物語を通じてLaravelを本当に身につけられるか。学ぶ順番と前提知識、一つの章で教える量、各場面で「何を理解し、どう確かめるか」、誤解を生む演出の有無、既習内容の復習とつながり、公式ドキュメントとの整合。物語の都合で学習が崩れていたら指摘し、学びが物語の動機になる形を提案する |

作中人物（物語・世界観に関わる議題のとき追加）：議題に関係する人物を選び、1つのサブエージェントにまとめて担当させる。各人物について「この展開で、行動・感情・知識に無理がないか」「動機が学習内容と噛み合うか」を、一人称の短い独白（仮想と明示）＋分析で返させる。人物の事実は正本の資料の範囲で扱い、未確定の設定を確定させない。

## 3. 独立に検討させる

- Agent ツールで、役ごとに**別のサブエージェントを同時に**起動する（`run_in_background: true`）。
- 全員に同じ議題・目的・制約・資料パスを渡す。他の参加者の意見は見せない。
- 依頼は検討だけ。ファイル変更・commit・push はさせない。
- 各自の出力：冒頭に確認した範囲を1行、要点2〜4件（根拠または仮定・影響・具体的な改善案または確認方法・該当箇所）。
- 裏設定は「参加者には共有するが、提案の中でゲーム内に明かす案を出さない」と明記する。

## 4. 統合して返す（親）

全員の結果がそろってから、次の順でまとめる。多数決や平均で結論を決めない。

1. **一致点**：複数の立場が独立に挙げたもの（誰が挙げたか、重さ🔴🟡🟢）
2. **立場ごとの重要な指摘**：一人だけが気づいた重要事項も残す
3. **対立点**：前提・ユーザー像・目的の違いとして説明し、解消に必要な確認を示す
4. **作中人物の声**（参加した場合）：独白の抜粋と、見つかった整合性の問題
5. **決めてほしいこと**：最大4問。各問におすすめの答えと理由を付ける（grilling の形式：❓ **Qn** - **題** … ➡️ おすすめ）

ユーザーが答えたら、それを前提に次の論点へ進む。必要なら同じ参加者に `SendMessage` で追加検討させる。

## 注意

- 円卓の結果は検討であって、ユーザーの承認ではない。決定はユーザーの回答で行う。
- 実プレイやユーザー調査をしていない限り、その旨を明記する。
- 画像が要る案は、担当分担（`/agent-coordination`）に従って Codex へ依頼する前提で書く。
