# CodeChronicleのゲーム素材

制作の判断と組み込みを担当する。共通の美術基準は [art-direction](../../../docs/art-direction.md)、用途・登録先・対応状況の入口は [制作案内](../../../docs/production/index.md) を参照する。細かく可愛いSFC時代のRPGという方向性を既存の実画面と揃える。

## 用途から仕様を選ぶ

| 用途 | 共通仕様 |
|---|---|
| キャラクターの会話用画像 | [会話用画像](../../../docs/production/uses/dialogue-portraits.md) |
| マップ用の人物・生物・敵 | [マップ用画像](../../../docs/production/uses/map-sprites.md) |
| 歩行 | [歩行](../../../docs/production/uses/walking.md) |
| 攻撃・戦闘用の絵や連続ポーズ | [攻撃・戦闘表現](../../../docs/production/uses/combat-art.md) |
| 地形・建物・小物 | [環境素材](../../../docs/production/uses/environment-art.md) |
| 開閉・表情・衣装などの差分 | [状態差分](../../../docs/production/uses/state-variants.md) |
| タイトル・物語・戦闘の背景 | [背景](../../../docs/production/uses/backgrounds.md) |

該当する仕様と対象の固有情報だけを読む。人物の確定特徴は [人物案内](../../../docs/production/characters.md)とそこから参照する各人物設定を使う。騎士・主人公の特徴をこのSkillへ直接書かず、対象にかかわらず再利用できる手順にする。過去のプロンプトは[制作履歴](../../../docs/production/records.md)であり、現在の共通規則そのものとは扱わない。

## 制作・組み込み

1. 依頼が生成・編集・品質レビューのどれか判断し、実際の表示側と対象の登録先を追う。複数用途がある対象はマップ・会話・遭遇・戦闘など必要な経路を別々に確認する。
2. 良好な既存画像を目視し、人物同定・絵柄・構図の役割を分ける。参照として生成へ渡した画像と、見ただけの画像を混同しない。ラスター生成・編集では利用可能な `imagegen` スキルを読み、組み込みツールを基本として従う。
3. 共通美術基準＋用途別仕様＋対象固有の特徴から具体的なプロンプトを組む。編集では変える部分と維持する部分を明示し、既存の文脈にない特徴を足さない。「pixel art」だけの指定や大きなPNGだけで品質を保証しない。
4. 最終候補を版付きでプロジェクト内へ保存する。実寸・alpha・crop・anchorを測り、実行コードの正本へ登録する。画像の余白、論理マス、表示px、衝突判定を区別し、見た目だけの依頼で進行や当たり判定を変えない。
5. 既存素材と同じ表示サイズで比較し、輪郭・描き込み・配色・材質・足元・透過・欠けを確認する。PC/スマホ、歩行方向、開閉など変更した経路を実画面で確認する。表示側の問題なら生成を繰り返す前にcropやCSSを調べる。
6. 画像/登録を変更したら `npm run check:art`、対象に必要な表示・通行テスト、`npm run build` を実行する。検査のPASSと美観の合格は別。制作ルールだけの変更ではSkillの構文と参照先を確認し、画像を生成しない。

## 記録と報告

[履歴ひな形](../../../docs/production/templates/record.md)で実際の参照・最終指示・生成方法・保存先・採否・検証結果を記録する。通常は `docs/art/` に置き、[索引](../../../docs/production/records.md)へ追加する。実測値の管理元は実行コードに置き、履歴の数値を現在値として二重管理しない。

変更素材、反映した表示箇所、検証、保存先、未対応を簡潔に報告する。レビューだけなら画像を差し替えない。制作依頼からcommit・push・公開まで自動で広げない。
