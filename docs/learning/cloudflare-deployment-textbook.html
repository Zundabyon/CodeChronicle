00 冒険の地図と、この本の使い方

まず、何ができるようになる？

  • 今のゲームが、どこで動き、どこに保存しているかを説明できる。

  • 画像・フォント・ゲーム・セーブを確認し、問題があれば戻せる。

01 現在地：CodeChronicleは何で動いている？

ブラウザがゲーム本体を動かしている

現在のCodeChronicleはReactとTypeScriptで書かれ、Viteで公開用ファイルへ変換されるアプリです。GitHub Pagesは完成したHTML・CSS・JavaScript・画像を配っています。

text
開発する場所                 公開用に変換       配る場所
src/ + public/  ── Vite ──>  dist/  ──>  GitHub Pages
                                              ↓
                                  ブラウザでゲームが動く
                                              ↓
                                  そのブラウザにセーブ

src/にはゲームの処理や問題の定義、public/には地図・キャラクター・背景・フォントなどがあります。dist/はその材料から作る配布物です。編集するのは材料側。dist/を手で直しても、次のビルドで作り直されます。

今は、サーバーのDBに問題や冒険を置いていない

問題はソースに定義され、ビルドしたJavaScriptに含まれます。冒険はブラウザのlocalStorageへ保存されます。学習問題にLaravelやPHPのコードが出てきても、公開サーバーでLaravelが動いているわけではありません。

そのため最初の移管は「完成したゲームを配る場所の変更」で進められます。PHPサーバーやDBを同時に引っ越す作業はありません。

手を動かす：package.jsonのbuild、src/、public/を開き、材料と配布物の違いを確認する。

小問：Cloudflareへsrc/App.tsxだけを置けば動く？ → 動かない。アプリ全体をビルドしてできるdist/を配る。

02 行き先：WorkersとPages、どちらにする？

この本はWorkers Static Assetsを使う

Cloudflare公式は、新しい静的サイトやSPAの公開先にWorkers Static Assetsを推奨しています。Pagesも引き続き利用できます。この本では、現在のゲームを静的ファイルとして配り、将来APIを足す道筋も作りやすいWorkersを選びます。[S1]

名前今回どう関わる？
Workers Static Assetsdist/を配る。今回の本編の行き先
Workersのサーバー処理将来APIを作るときに追加する処理
Pages別の公開サービス。補講Aで設定を比較
D1将来、問題などをSQLで管理する候補
R2将来、大きな画像や音声を置く候補

「Workers」という名前でも、最初からサーバー側のプログラムを書く必要はありません。今回は静的ファイルを指定するだけの構成です。[S1]

text
今回：ブラウザ ──> Workers Static Assets ──> distのゲーム

将来：ブラウザ ──> Worker API ──> D1など

学びを混ぜすぎない

今回はCloudflare Viteプラグインを入れず、既存のViteでdist/を作り、Wranglerで公開します。プラグインを使う別方式の記事にはdist/clientなどが登場しますが、この本の出力先はdist/です。

小問：Workersを選んだら、問題は自動でD1へ入る？ → 入らない。保存先の変更は別の設計・実装が必要。

03 セーブの引っ越しが、いちばん大切

URLが変わると、冒険が見えなくなることがある

localStorageはオリジンごとに分かれます。オリジンは「プロトコル・ホスト名・ポート」の組み合わせです。GitHub PagesとCloudflareはホスト名が変わるため、同じブラウザでも保存場所が別になります。[S2]

text
旧：https://zundabyon.github.io/CodeChronicle/
新：https://実際に発行された名前.workers.dev/

旧URLのセーブ箱 ≠ 新URLのセーブ箱

URLのパスが変わるだけなら同一オリジンですが、今回の引っ越しはホスト名が変わります。「続きから」が出ないことだけでは、旧セーブが削除されたとは判断できません。

既存の書き出し機能を使う

  1. 旧URLを、いつも遊んでいるブラウザ・プロファイルで開く。
  2. タイトルの「冒険の管理」から「セーブファイルの書き出し・読み込み」を開く。
  3. 「セーブを書き出す」でJSONを保存する。
  4. ファイルが空でないことと、保存した場所を確認する。
  5. 名前・レベル・現在地をメモし、ファイルを残しておく。

自分のセーブは、自分の端末で書き出します。運営者の手元から、全プレイヤーのlocalStorageを一括回収することはできません。

重要：旧URLは、引き継ぎが終わるまで開ける状態で残します。新URLへの自動転送を先に入れると、旧画面から書き出しにくくなります。

今日のセーブポイント：JSONを書き出せた。まだ新URLへ読み込まなくて大丈夫。

04 移管の順序と、変更するファイル

二段階で進める

前半は「試しに新URLで動かす」。後半は「正式なURLを決め、引き継ぎ案内をして切り替える」です。旧サイトを先に停止する必要はありません。

  → ローカル確認 → 新URLで公開・確認
  → 正式URL決定 → セーブ引き継ぎ
  → 案内・リンク更新 → 旧公開の運用を整理

06 画像が消える理由：baseを理解する

GitHub Pagesと、今回のCloudflareは入口が違う

現在のGitHub Pagesは/CodeChronicle/という場所の下にあります。既存workflowも--base=/CodeChronicle/でビルドしています。今回のWorkers公開はホスト直下の/を入口にします。

text
GitHub Pages用： /CodeChronicle/assets/...
Cloudflare用：   /assets/...

Viteのbaseは、公開先に合うようにファイルへの道筋を調整する指定です。HTML・CSS・importされた画像などの参照に反映されます。[S3]

bash
# Cloudflare用
npm run build -- --base=/

# 旧GitHub Pages用の指定
npm run build -- --base=/CodeChronicle/

両方とも同じdist/を作り直します。最後にどちらでビルドしたかを忘れないよう、公開の直前には公開先に合うビルドをやり直します。

CodeChronicleで確認する場所

ゲームの画像参照にはimport.meta.env.BASE_URLが使われています。タイトルのローカルフォントも確認対象です。新しい画像を足すときも、GitHub PagesのURLを直接埋め込まないようにします。

手を動かす：dist/index.htmlをエディタで開く。assets/へのパスが/CodeChronicle/のままになっていないか見る。ブラウザではファイルを直接ダブルクリックせず、次節のサーバー経由で確認する。

小問：ドメインが同じならbaseも必ず同じ？ → パス以下に置く構成か、ホスト直下かで変わる。

07 Wranglerと、公開の設計図

プロジェクトに道具を入れる

bash
npm install -D wrangler@4
npx wrangler --version

この操作でpackage.jsonとlockファイルが変わります。グローバルに入れるより、プロジェクトに登録すると他の環境でも同じ道具を使いやすくなります。[S4]

リポジトリ直下に、次のwrangler.jsoncを作ります。nameは自分のアカウントで使う名前を選んでください。同名の既存Workerがあれば更新対象になり得るため、新規実習なら既存と重ならない名前にします。

jsonc
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "codechronicle",
  "compatibility_date": "2026-11-03",
  "assets": {
    "directory": "./dist"
  }
}

compatibility_dateはWorkerランタイムの動作基準日です。新規作成時点の日付を指定し、後で更新するときは動作確認します。ファイルの公開日や有効期限ではありません。[S1]

assets.directoryは配るフォルダ。今回は静的配信のみなのでmainは不要です。nodejs_compatや空のサーバーファイルも、この最小構成では追加しません。[S1]

.gitignoreに追記する

gitignore
.wrangler/
.dev.vars*
.env*
!.env.example

秘密の値は.env.exampleにも書きません。Wranglerのログイン情報やAPIトークンを、ソースやチャットへ貼らないようにします。

11 冒険の記録を新URLへ持っていく

正式に使うURLで読み込む

後から独自ドメインを付けるなら、正式URLを決めてから本物のセーブを読み込むと移動が一度で済みます。workers.devから独自ドメインへ変える場合も、localStorageの保存場所は変わります。[S2]

  1. 旧URLで書き出したJSONを手元に用意する。
  2. 新しい正式URLを、保存したいブラウザで開く。
  3. 「冒険の管理」から、セーブファイルの読み込みを開く。
  4. 「セーブファイルを選ぶ」でJSONを指定する。
  5. 表示された名前・レベルを確認する。
  6. 合っていれば「このセーブを読み込む」。違えば「取り消す」。

13 独自ドメインは、別の小さな引っ越し

最初はworkers.devで十分

独自ドメインは必須ではありません。使うなら、継続して使えるURLを正式な入口として決めます。ドメインの購入先をCloudflareへ移す作業と、公開先をCloudflareへ移す作業は分けて考えられます。

WorkersのCustom Domainには、有効なCloudflare zoneと、そのドメインの管理権限が必要です。github.ioのように自分が管理していないドメインを、そのままCustom Domainへ持っていくことはできません。[S9]

設定の流れ

  1. 自分が管理するドメインをCloudflareで有効にする。
  2. Worker → Settings → Domains & Routesを開く。
  3. Add → Custom Domainから使うホスト名を登録する。
  4. 発行されるDNS・証明書の状態と、HTTPSで開けることを確認する。
  5. その正式URLでも、10節の確認表を実施する。

Cloudflareが必要なDNSレコードと証明書を設定します。同じホスト名に既存CNAMEがある場合は競合するため、既存サービスの用途を調べてから整理します。用途不明のDNSレコードをまとめて削除しないようにします。[S9]

正式なドメインはwrangler.jsoncのトップレベルにも記録し、以後の公開と設定を揃えます。次は追加部分の例です。実際に所有するホスト名へ置き換え、既存のassetsなどは残し、項目間にカンマを付けます。[S9]

jsonc
"routes": [
  { "pattern": "game.example.com", "custom_domain": true }
]

URLとセーブを一緒に考える

workers.dev、独自ドメイン、wwwあり・なしは、それぞれ保存先が分かれる場合があります。正式な入口を一つ決めて案内します。移動前のURLで最新セーブを書き出し、正式URLへ読み込み直します。[S2]

16 料金・制限と、秘密の置き場所

運用で見るもの：公開失敗、ファイルサイズ、読み込み速度、Buildの利用枠、将来追加するAPI・D1・R2の利用量。予算と通知を決めてからサービスを増やします。

このAPIは読取専用です。管理用の追加・編集APIは公開しません。SQLにURLの文字を連結せず、値はbindで渡します。D1 Binding API ↗

ts
export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url);
    if (url.pathname !== '/api/catalog') {
      if (url.pathname === '/api' || url.pathname.startsWith('/api/')) {
        return Response.json({ error: 'not_found' }, { status: 404 });
      }
      return env.ASSETS.fetch(request);
    }
    if (request.method !== 'GET') {
      return Response.json({ error: 'method_not_allowed' }, {
        status: 405, headers: { Allow: 'GET' }
      });
    }

    const version = url.searchParams.get('version');
    if (version !== null && !/^[A-Za-z0-9._-]{1,64}$/.test(version)) {
      return Response.json({ error: 'invalid_version' }, { status: 400 });
    }

    try {
      const release = await env.DB.prepare(`
        SELECT version FROM catalog_releases
        WHERE status = ? AND (? IS NULL OR version = ?)
        ORDER BY published_at DESC, version DESC LIMIT 1
      `).bind('published', version, version).first<{ version: string }>();
      if (!release) {
        return Response.json({ error: 'catalog_not_found' }, { status: 404 });
      }

      const rows = await env.DB.prepare(`
        SELECT q.payload_json
        FROM catalog_entries e
        JOIN question_revisions q
          ON q.question_id = e.question_id
          AND q.revision = e.question_revision
        WHERE e.catalog_version = ? ORDER BY e.question_id
      `).bind(release.version).all<{ payload_json: string }>();
      if (!rows.results.length) throw new Error('empty_catalog');
      const questions = rows.results.map(row => JSON.parse(row.payload_json));
      return Response.json({ catalogVersion: release.version, questions }, {
        headers: { 'Cache-Control': 'no-store' }
      });
    } catch {
      console.error('catalog_load_failed');
      return Response.json({ error: 'catalog_unavailable' }, { status: 503 });
    }
  }
};

shared/catalog.ts：外部データを検証する

TypeScriptの型注釈だけでは、ネットワークから来たJSONを検証できません。以下は現在のQuestionの形に合わせた入口です。本番の公開前検証では、クエストの参照や採点の意味も追加で確かめます。

ts
import type { Question } from '../src/content';
export type Catalog = { catalogVersion: string; questions: Question[] };
const record = (v: unknown): v is Record<string, unknown> =>
  typeof v === 'object' && v !== null && !Array.isArray(v);
const strings = (v: unknown): v is string[] =>
  Array.isArray(v) && v.every(x => typeof x === 'string' && x.trim() !== '');

function isQuestion(v: unknown): v is Question {
  if (!record(v)) return false;
  if (typeof v.id !== 'string' || !v.id.trim()) return false;
  if (typeof v.difficulty !== 'string' || !['beginner','intermediate','advanced'].includes(v.difficulty)) return false;
  if (typeof v.topic !== 'string' || !['frontend','laravel','connection'].includes(v.topic)) return false;
  if (typeof v.kind !== 'string' || !['choice','cli','fill-choice','fill-input'].includes(v.kind)) return false;
  for (const key of ['prompt','reveal','explanation']) {
    if (typeof v[key] !== 'string' || !v[key].trim()) return false;
  }
  if (v.track !== undefined && v.track !== 'react' && v.track !== 'vue') return false;
  if (v.inertia !== undefined && typeof v.inertia !== 'boolean') return false;
  for (const key of ['filename','code']) {
    if (v[key] !== undefined && typeof v[key] !== 'string') return false;
  }
  if (v.options !== undefined && (!strings(v.options) || v.options.length !== 4)) return false;
  if (v.accepted !== undefined && !strings(v.accepted)) return false;
  if (v.answer !== undefined &&
      (typeof v.answer !== 'number' || !Number.isInteger(v.answer) || v.answer < 0 || v.answer > 3)) return false;
  if (v.kind === 'choice' || v.kind === 'fill-choice') {
    return strings(v.options) && v.options.length === 4 && typeof v.answer === 'number';
  }
  return strings(v.accepted) && v.accepted.length > 0;
}

export function parseCatalog(value: unknown): Catalog {
  if (!record(value) || typeof value.catalogVersion !== 'string' ||
      !/^[A-Za-z0-9._-]{1,64}$/.test(value.catalogVersion) ||
      !Array.isArray(value.questions) || !value.questions.length ||
      !value.questions.every(isQuestion)) throw new Error('invalid_catalog');
  const questions = value.questions;
  if (new Set(questions.map(q => q.id)).size !== questions.length) {
    throw new Error('duplicate_question_id');
  }
  return { catalogVersion: value.catalogVersion, questions };
}

B06 既存ゲームへ接続する：ここが移行の本体

APIの成功と、ゲーム移行の完了は別

現状のゲームは、起動時からコード内の問題がある前提です。非同期に変えると、保存の検証とゲーム開始の順番も変わります。

このリポジトリで実装した接続を試す（2026-11-03）

毎回の起動はnpm run dev:stagingの1コマンドで実行できます。ビルド→ローカルDB準備・問題投入→起動を順に実行し、途中で失敗したら止まります。起動中のWranglerはCtrl+Cで止めてから実行します。以下は内訳を理解するための個別手順です。

既存253問をGit原稿から書き出し、D1の固定版としてゲーム開始前に取得する実装を追加しました。通常ビルドは従来方式、build:stagingがAPI方式です。以下でローカルを試せます。

本番WorkerにGitを接続し、Production branchをmain、Root directoryをリポジトリ直下にします。基礎編の静的公開設定から、Deploy commandを本番用の設定指定へ変えます。Workers Builds ↗

worker-configuration.d.tsは生成した型としてGitに含める運用なら、ビルド時に再生成しなくても検査できます。DB接続設定を変えたときは型も更新します。設定ファイルにAPIトークンを直書きしません。

問題更新の流れ

text
Gitで原稿を変更
 → 型・正解・参照IDを検証
 → 新revisionと新catalogをdraftで投入
 → 件数・整合性を照合
 → 対応するアプリと組み合わせて試験
 → 公開版を切り替える

DBのschema変更と問題データの公開は、単なるゲームの再ビルドとは別の操作です。初期はDB変更を無条件に毎回のBuildへ詰め込まず、適用対象と互換性を確認してから行います。

旧アプリと新カタログ、新アプリと旧カタログの組み合わせも考えます。カタログ取得に対応アプリ版の条件を追加するか、旧版を明示指定して使う方式を決めます。この契約が未実装の間は、アプリと問題を独立に更新できる完成形とは扱いません。

確認すること：mainの更新で試験用DBに接続していない。プレビューは本番へdeployせず、試験用の設定・DBを使っている。

B10 戻し方と、卒業課題

戻す対象は3つ

対象戻す手段
ゲーム・Worker正常なデプロイ版へ戻す。Git側にも修正を反映
問題カタログ対応する旧版を選べる契約で戻す。公開済み内容を上書きしない
DBの誤更新バックアップ・Time Travel等を使う復旧を別に用意

Workerの版を戻しても、D1の内容やブラウザのセーブは戻りません。D1のTime Travelによる復元はDB全体を上書きする操作なので、練習は試験用DBで行い、実行対象・復旧点・影響範囲を確認します。D1 Time Travel ↗

この実習コードで足りない部分を把握する

  • 全問題の抽出・投入・照合スクリプト。
  • 既存App、保存検証、依頼・本・ボスの接続作業。
  • セーブ形式の版移行と、旧問題IDの解決。
  • アプリ版と問題カタログ版の互換チェック・選択の仕組み。
  • 本番相当の障害試験、監視、利用量・費用の記録。

これらはCodeChronicleの移行実装として行う作業です。本書のサンプルは、D1とWorkerの最初の1往復を学ぶためのものです。

卒業課題

  1. 試験DBから問題を取得し、1問回答できる。
  2. 通信失敗で元のセーブが変更されず、再試行で再開できる。
  3. DBにだけ存在する問題を解き、再読込しても履歴が残る。
  4. 旧URLのJSONを正式URLへ引き継ぎ、依頼・復習を続けられる。
  5. 問題の更新後でも冒険中の出題・採点は同じ版で、前版への復帰を実演できる。

説明できれば合格：「何を公開し、どこに保存し、失敗したとき何を残して戻すか」を自分の言葉で言う。
