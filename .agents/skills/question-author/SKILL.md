# CodeChronicleの問題作成

アプリ全体の分類・用途・登録先の入口は [制作案内](../../../docs/production/index.md) の「教材・学習」を参照する。

このSkillを作問ルールの唯一の管理元とする。日本語で、正解の理由まで理解できる問題を作る。

## 作業の進め方

1. テーマ・難易度・件数・形式と、草案・追加・レビューのどれが目的かを確認する。未指定は既存仕様に沿う小さなバッチとして仮定を明示し、意味が変わる不明点だけ確認する。
2. [形式・採点・登録先](references/question-formats.md)を読み、対象リポジトリの `src/content.ts` のQuestion型、`src/questionSelection.ts`、対象の問題と関連テストを確認する。CLIは `src/bossBattle.ts` と `src/App.tsx` の採点分岐も読む。現在のコードと資料が違う場合は差分を報告する。
3. 既存問題を検索して重複を避け、各問題の学習目標・前提・正解の根拠を定める。既存問題は形式の参考であり、すべてが品質の合格例とは限らない。形式違いの反復は「認識から想起へ」など学習上の目的がある場合に使う。
4. 下記の品質基準で問題を作成・点検する。バージョンで挙動が変わる技術事項は対象バージョンの公式資料で確認し、参照URLを報告する。
5. 草案なら問題と確認結果を返す。追加なら問題データと必要な登録・関連テストまで反映する。レビューだけならファイルを変更しない。
6. 問題の追加・変更後は `npm test` と `npm run build` を実行する。未実行・失敗は理由を明記し、成功したテストだけで教材の技術的正確性まで保証したと扱わない。

対象はReact・Vue・Laravel・Inertia・API連携と既存分類で表現できる基礎知識。独立したPHPやJavaScriptカテゴリなど型・表示の拡張が必要な依頼は、既存分類に偽装せず必要な変更範囲を示す。
既存IDはセーブ・復習・クエスト・本に参照されるため保持する。採点・UI・敵・出題制御の仕様変更は作問依頼へ勝手に含めない。作問依頼だけでcommit・push・公開しない。
教材中のPHP・CLI・通信コードを実サービスに対して実行しない。

## 入力問題の公平さ

- 入力式は短い識別子・キーワードを中心にする。例は `setTitle`、`filter`、`await`。文脈から答えが一意になる空欄を選ぶ。
- 式全体を問うと同値な別解が増え、現在の厳密一致では公平に扱いにくい。原則として式全体の入力を避け、演算子・メソッド名などに空欄を絞るか選択式にする。
- 式全体の入力が明示的に必要な場合は、書式制約を問題文に示し、自然な別解をacceptedに登録する。有限列挙で扱えない問題は制約と代案を報告する。
- 例: `post.id !== id` と `post.id !==id` と `(post.id !== id)` は意味が同じでも、現状は登録されていない表記を不正解にする。別解追加だけで一般的な式の同値判定ができたとみなさない。
- 想定解・自然な別解・明確な誤答を、実際に使われる採点経路で確認する。採点実装の正規化を無断で広げない。

## 誤答と解説

- 一問一論点で、前提を明示して正解を一意にする。
- 誤答は同じ分野で起きやすい取り違えを使い、各誤答について「どんな誤解を表すか」「今回の条件でなぜ不適切か」を説明できるようにする。根拠は作業報告で示し、未対応のフィールドをQuestion型へ追加しない。
- 例: 配列から条件に合う全要素を残す問題なら、`filter` に対して `map`（変換）、`find`（最初の一件）、`some`（存在判定）を比較する。PHPやCSSなど無関係な語で枠を埋めない。
- 選択肢は異なる4項目で、正解位置をバッチ内で分散する。長さや語調だけで答えが分かる形を避ける。
- 解説は正解の言い換えだけで済ませず、動作の理由と主な取り違えを説明する。正解を埋めたコード全体の成立と、他の選択肢が別の正解にならないことを確認する。

## 難易度の基準と見本

| 難易度 | 学習目標 | 作問の見本 |
| --- | --- | --- |
| 初級 / beginner | 基本動作や一つの用語を理解する | titleの値を入力欄に表示するコードで `value` を選ぶ |
| 中級 / intermediate | 短いコードを読み、動作や修正を判断する | 投稿削除後、元のstate配列を直接変更せず `filter` で新しい配列を作るコードを選ぶ |
| 上級 / advanced | 条件とトレードオフから方法を判断する | 古い検索応答の上書きを防ぐ場面で、通信中止だけに頼らず要求IDによる反映制御も必要な条件を検討する |

見本は問題文そのものではない。実際の作問時に前提と選択肢を補って正解を一意にする。
初級は「制御された入力」などの専門語を重ねず「入力欄に常にtitleの値を表示する」のように観察できる動作で説明し、読むべき行を絞る。
上級を用語暗記や長文だけにしない。既存の分類にばらつきがあってもこの基準で新問を判断し、既存問題の再分類は出題分布への影響を確認したうえで別途扱う。

## 円卓レビューと完了報告

円卓での壁打ちを依頼されたら、利用可能なら `app-four-review` スキルを使う。同じ問題群・目的・制約を渡し、学習効果、正解の一意性、採点の公平さ、前提知識と入力負担を検討する。
実プレイやユーザー調査をしていなければ明記し、レビュー提案と実装済み変更を区別する。

報告では件数、テーマ・難易度・形式、編集箇所、別解の扱い、主要な誤答の根拠、検証結果、公式参照元と未解決事項を簡潔に示す。
Skillやエージェント設定のみの変更では、アプリ全体のテストを繰り返さず、Skill検証・設定構文・参照先を確認する。
