# コードレビュー

変更を実装したエージェントとは別のレビュワーで、実際に起きる問題を根拠付きで評価する。手順の管理元はこのSkillとし、`code_reviewer` エージェント定義には複製しない。

## 対象を固定する

親エージェントは依頼内容、期待する動作、対象リポジトリ、baseと対象差分を揃える。PRならbase/headのコミットIDを確認し、作業ツリーなら追跡済み・未追跡・ステージ済みを含む依頼範囲を明示する。差分だけで判断できない場合は周辺コード、呼び出し元、既存テストや仕様を読む。

作業中の変更をレビューする場合は、差分のパッチと必要な未追跡ファイルを一時領域へ保存するなどして、どの版を見たか再現できるようにする。base/head、ファイル一覧、パッチのハッシュ等で対象版を記録し、レビュー中に実装が変わったら混同しない。

## 独立レビューと相互検証

親としてレビューをまとめる場合は次の流れで進める。

1. 原則、実装者とは別の2レビュワーを起動する。両者へ同じ対象版・要件・確認範囲を渡し、最初の回答までは他方の指摘や親の結論を渡さず独立評価させる。実装者の自己レビューは補助情報として扱い、これだけで完了にしない。
2. 初回結果が両方揃ったら互いの指摘を渡す。各レビュワーは相手の指摘についてコードや実行結果を確認し、「支持・反証・未確認」とその根拠を返す。反証された側は必要なら指摘を訂正・撤回する。
3. 相互検証は最大2往復で止める。親は重複をまとめ、根拠の強さで採否を判断する。人数、肯定派・否定派などの演技、全員一致を判定基準にしない。解消できない不一致と未確認事項は残す。

`code_reviewer` などとしてレビューを割り当てられた側は、指定された独立評価または相互検証を行い、親へ返す。自分からレビュワーを増やさない。実装者との同一性は名前だけでなく、当該変更を実装したかどうかで判断する。

環境が並列起動できなくても、別エージェントへ順に同じ資料を渡せるなら独立評価は可能。別レビュワーを確保できない場合は可能な範囲で評価し、人数と独立性の不足を明記する。自己レビューを独立レビュー完了として報告しない。ユーザーが人数や手順を指定した場合はその指定を優先し、実施した体制を報告する。

## 調べること

変更に関連する実害を優先する。バグ、既存動作の回帰、エラー・境界条件、データやセーブの互換性、採点の公平さ、アクセス制御やセキュリティを、実際の変更に応じて選ぶ。毎回すべての軸を形式的に確認する必要はない。

- 仕様・呼び出し元・データ形式を根拠に発生条件を確かめる。意図された仕様変更や好みだけの違いを不具合にしない。
- テストや再現操作は指摘の確認に必要な範囲で行い、実行した内容と結果を記録する。未実行・実行不能・推測は確認済みの事実から分ける。
- 根拠を探しても問題がなければ指摘0件でよい。件数や対立を作るために問題を捏造しない。

## 指摘と統合結果

各指摘には次を含める。短い指摘で伝わる場合は項目を文章にまとめてよい。

- **位置**: 対象版の `file:line`。可能なら変更行を起点にし、関連箇所も示す。
- **発生条件・影響**: どの入力や状態で何が壊れるか。期待する動作の根拠も示す。
- **優先度**: P0 = 広範囲で即時対応が必要な致命的障害、P1 = 主要動作・データ・安全性を損ない早期修正が必要、P2 = 条件付きの不具合として修正が必要、P3 = 影響の小さい具体的不具合。単なる改善案は不具合と分ける。
- **検証状態と根拠**: 再現済み／コード上で確認／未確認仮説。再現手順・実行結果、または成立するコード経路を添える。
- **相互検証**: 他方の支持・反証・未確認と根拠。未合意なら両方の論点と解決に必要な確認を残す。

親の最終報告は重要な指摘から並べ、対象版、レビュー体制、実施した検証、残る不一致・未確認範囲を簡潔に添える。未確認仮説は確定指摘に混ぜない。「指摘0件」は確認範囲内の結果であり、未検証範囲まで安全と断定しない。

## 修正と再レビュー

レビュー依頼だけではファイル修正、commit、push、外部へのコメント投稿を行わない。修正も依頼されている場合は、指摘を実装担当へ返して修正させる。修正後は別レビュワーが新しい対象版で当該問題と影響範囲を再確認する。

レビュー中・修正後に差分が更新されたら、旧版への判断をそのまま完了扱いにしない。更新された差分と関連経路を再検証し、どの指摘が解消・継続・新規になったかを記録する。全体の対象や前提が変わった場合は、独立評価からやり直す。
